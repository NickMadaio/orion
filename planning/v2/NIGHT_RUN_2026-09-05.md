## Two findings that changed the briefs

### The endpointing number is already turned up, and it still cuts him off

`defaults read com.nickmadaio.orion.app` on his machine:

```
OrionVoiceEndpointingMs   = 1400      (default 900)
OrionVoiceUtteranceEndMs  = 2600
OrionVoiceAppleFinalGrace = 1.8
OrionSTTProvider          = deepgram
OrionTTSProvider          = elevenlabs
```

He has already pushed the silence threshold from 900 ms to **1400 ms** — nearly a
second and a half of dead air before Orion is allowed to answer — and Orion
*still* cuts him off. That is the evidence that ends the argument: **a fixed
silence threshold cannot solve this.** Turning it up further only trades one
complaint ("he interrupts me") for the other ("he takes forever to answer"), and
he is already paying that second cost.

The turn-taking fix has to be adaptive — transcript stability, punctuation,
last-word confidence, and explicit continuation signals ("hold on", "I'm not
done") — with the partial transcript PRESERVED and appended to when endpointing
fires early, rather than a new disconnected request. `vad_events=true` is already
being sent to Deepgram, so the `SpeechStarted` signal needed for hands-free
barge-in is already arriving; nothing is listening for it during speech.

### The music problem is a Bluetooth profile switch, not a ducking bug

`system_profiler SPAudioDataType`, run tonight:

```
Sony WH-1000XM4    Default INPUT  : Yes   1 ch @ 16000 Hz   Bluetooth
Sony WH-1000XM4    Default OUTPUT : Yes   2 ch @ 44100 Hz   Bluetooth
MacBook Pro Microphone            :       1 ch @ 44100 Hz   Built-in
```

**His headset is both the default input and the default output.** Apple documents
what follows: selecting a Bluetooth headset's microphone switches the device out
of high-quality listening mode into bidirectional voice mode, and playback
collapses with it. That is precisely "the second I start talking to Orion the
audio is terrible" — the ducking is not the cause, and no amount of masking will
recover the bandwidth.

Nick assumed the loss was unavoidable and asked us to mask it. It is probably
avoidable: capture from the **built-in MacBook Pro microphone** whenever output is
Bluetooth. The headphones never leave the high-quality profile, and the ducking
goes back to being what he actually asked for — a dip in volume.

The duck also has to span the whole exchange. Today `AudioDucking` restores on
leaving `.listening`, so the music comes back up **while Orion is still talking
over it** — the worst possible moment, and probably half of why the current
behaviour feels broken.

### `native/Orion/Sources/Orion/RunTimeouts.swift` — a race nobody had noticed

The three competing ceilings were worse than "inconsistent". The client's hard
read deadline was `180 + 30 = 210`, and the app's `.thinking` watchdog ceiling
was **also 210**. A tie, not an ordering. Whichever runloop got there first
decided what Nick saw, so one underlying failure produced either the specific
gateway error or the watchdog's generic "That question never came back" — at
random, run to run. A backstop that races the thing it is backing up is not a
backstop, and it explains why the same symptom never looked the same twice.

The second half is worse and still latent: the 600s in `openclaw.json` is a
*default*, harmless only while the app keeps passing `--timeout` explicitly.
Delete that one argument while tidying an argument list and the agent runs to
600s while the client gives up at 210s — the work completes, into a pipe nobody
is reading, and Nick is told it never came back. That is his reported fault
exactly: "i cant tell if hes actually working".

The file now states the ORDERING as a check rather than three literals as
comments, so a future edit that moves one number without its neighbours fails a
named assertion:

```
agentTimeout(300) < terminateAt(320) < killAt(325) < clientReadDeadline(360) < watchdogCeiling(420)
```

It also raises the agent's own timeout from 180s to 300s, with a reason: Nick
timed out asking Orion to update himself, which is a build, a copy and a
relaunch. 180s was not a safety limit for that job, it was a guarantee of
failure. What makes a long turn tolerable is the progress feed, not a short
deadline pretending nothing slow is legitimate.

**It is not wired in yet.** `GatewayClient` still carries its own 180. The file
is sound and inert; finishing that wiring is the first job of the next wave.
