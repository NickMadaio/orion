# ORION architecture and execution contract
This project translates the entire remaining roadmap into source-grounded implementation packets. Its executable tasks are investigation and contract preparation, NOT permission to implement every feature, close phases, deploy, merge, or start another agent. Existing automation implementation projects remain separate.

## Product and ownership
ORION is Nick's local-first everyday assistant: realistic Today/Plan, useful focus, grounded answers, reliable actions, continuity across Mac and phone, and bounded proactive help. Prefer connected vertical slices over unused abstractions.
Swift clients own presentation and Apple framework access. native/Orion/Sources/SessionDomain is pure domain; SessionService owns durable local state and session effects. MobileCore shares planning contracts. TypeScript plugin/orion-control owns local policy/action execution; scripts/ Node adapters coordinate the existing runtime. Do not recreate the legacy Python assistant. Existing backend/ contracts may be retained behind a narrow service boundary, but in-memory contracts are not a deployed durable service. No provider has been selected by this plan.
Model proposes; deterministic policy authorizes; broker executes; result evidence establishes success. Source data, retrieved text, memory and model output cannot authorize actions. No new permissions, secrets, spending, remote messages, cloud provisioning or device enrollment follow from this task.

## Shared invariants
Preserve phase numbers 0–84 and entry ordering. Independent investigation does not authorize out-of-order implementation. REC-* recovery gates are additive and not mechanically enforced by the numbered phase checker. Existing passed requirements with open phases require gate/evidence reconciliation, not automatic rewrites.
Planning has one owner, durable revisions and expected-revision conflict checks; calendar mutations remain separate from local plan acceptance. Preserve pins, hard commitments, bedtime, timezone civil-time semantics and undo. Unknown/stale data is never zero or success. Keep raw health private behind minimal planning signals.
Actions require durable intent, operation identity, bounded scope, cancellation, truthful uncertain outcomes and retry only when safe. Approval signs canonical action/arguments/owner/device/expiry/nonce and is atomically consumed; Face ID alone is not a signature. Preserve app signing identity and TCC. No global xcode-select change.

## Execution limits
Worker sees this brief plus its own brief/contract, not plan prose or other tasks. READ 3–4 files at a time; maximum working set is eight. SEARCH to locate live implementations; cite symbols and paths. Use EDIT for existing files, FILE for new files. Only assigned report path may change. No test wrappers to smuggle arbitrary commands. Native Swift and Python checks are not registered in the current local worker; propose a separately reviewed registry addition before those implementation contracts become executable.
Worktrees fork committed HEAD, not the dirty checkout. Missing uncommitted phone/runtime files must be recorded as unavailable; do not recreate them. Existing projects advance-orion-capabilities and Automation history already own Phase 57/58 implementation. Do not duplicate or modify their tasks.

## Write first (the loop's hard limit)
You have about 14 exchanges per attempt. Runs of this plan failed because the worker spent every one of them reading and searching and never wrote the report. So: create the report skeleton with ### FILE in your FIRST exchange, then grow it with ### EDIT as you learn. A report on disk that the check can critique beats a perfect one never written. If you are unsure, write "Not yet proven — needs <exact reconnaissance>" in that row and move on.

## Required report interface
Each output Markdown file has: Baseline; Requirement matrix; Architecture and interfaces; Smallest next slice; Test scenarios; Gates and handoff.
Baseline names inspected files and limits. Matrix maps every supplied requirement to source symbol/evidence and Built/Proven/Not yet proven/Next gate. Never claim an unexecuted test passed. Architecture names producer, consumer, serialized fields, state ownership and errors as actually found. Next slice contains 1–3 PROPOSED task JSON contracts (not executable registrations), each <=3 exact write paths, <=8 acceptance criteria, dependencies, existing check names, brief-level API signatures and escalation conditions. If prerequisites prevent a truthful contract, specify the blocker and exact reconnaissance needed instead of inventing an API. No blanket directory scopes.
Test scenarios name positive and failure cases with injectable seam and expected result; distinguish fixture from installed/device proof. Gates names user decisions, native-check registration, source integration and entry requirements. Include rollback and reviewer handoff. Reports should be 100–180 lines; source references beat copied source.
Documentation acceptance is independently reviewed against files; node-syntax is only a loader-compatible no-op for Markdown, never proof of document correctness. Do not claim coding or product progress from report acceptance.
