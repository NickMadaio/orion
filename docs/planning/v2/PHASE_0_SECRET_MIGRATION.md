## Chosen storage design

Use macOS Keychain-backed OpenClaw `exec` SecretRefs for the gateway,
Anthropic, and Ollama values. OpenClaw resolves them into its in-memory snapshot, uses
sentinels until provider egress, and preserves the last-known-good snapshot if
reload cannot resolve every active reference.

The proposed providers use `/usr/bin/security` directly, `jsonOnly: false`,
and one Keychain service per credential:

- service `ORION OpenClaw Gateway`, account `openclaw`
- service `ORION OpenClaw Anthropic`, account `openclaw`
- service `ORION OpenClaw Ollama`, account `openclaw`

The Keychain exec-provider shape passed `openclaw config set ... --dry-run`
against the current live schema. No Keychain item, config value, or runtime was
changed during that validation.

The complete value-free apply plan is versioned at
`docs/planning/v2/OPENCLAW_SECRETREF_PLAN.json` and generated by
`scripts/orion_v2_secretref_plan.py`. It uses the installed OpenClaw target
registry's canonical types for all three audit findings. The plan contains no
credential values, fingerprints, shell strings, or generic command execution.

OpenClaw's first apply dry-run accepted the target plan but rejected the exec
provider because `/usr/bin/security` is root-owned rather than owned by the
current user. The plan therefore sets `allowInsecurePath: true` only for this
fixed Apple/SIP-managed binary. Tests require the exact `/usr/bin/security`
path and forbid a shell field; the exception cannot select a runtime command.
With that narrow exception, dry-run advanced to live resolution and stopped at
the expected missing Keychain item. The target plan has therefore not yet
completed an end-to-end apply dry-run.

The Keychain seeding helper passed a disposable end-to-end proof on 2026-08-18:
it created a non-secret item through the native macOS Security framework, gave
only `/usr/bin/security` trusted access, read it through the same command route

A subsequent read-only check found all three intended live service names

## Coordinated apply gate

Do not apply while Nick or another agent is exercising the live Orion UI. The
apply requires a short coordinated gateway window because it changes runtime
credential resolution and calls `secrets.reload`.

During that window:

1. Re-run `openclaw secrets audit --json` and the no-cloud Orion doctor.
2. Run `scripts/orion_v2_keychain_seed.py --self-test-disposable`; the helper
   must prove native in-memory insertion, exact-command readback, and deletion.
3. Run `scripts/orion_v2_keychain_seed.py --status` read-only; refuse unexpected
   existing items for manual review, then use its explicit install confirmation
   to seed approved values. `--items` allows the gateway and Ollama values to be
   migrated without ever loading an unrotated Anthropic value.
   The helper does not put values in process arguments or terminal output,
   verifies read-back in memory, and rolls back newly added items on failure.
4. Generate an OpenClaw secrets plan targeting the gateway, Anthropic provider,
   and main-agent Ollama profile; compare it with the versioned plan.
5. Run `openclaw secrets apply --from <plan> --dry-run --allow-exec`.
6. Apply only if every reference resolves and target validation passes.
7. Call `openclaw secrets reload --json`; rely on its atomic last-known-good
   behavior if resolution fails.
8. Require `openclaw secrets audit --check` to return clean.
9. Run the no-cloud doctor, authenticated `orion_v2_live_smoke.py`, authority
   snapshot check, and full regression suites.

OpenClaw intentionally does not create plaintext rollback copies during secret
apply. Do not add another config backup containing the migrated values.

Python provider is either migrated to Keychain/SecretRef access or proven
unused. Removing it now could silently remove legacy fallback behavior.

Nick authorized deletion of the different July 27 `.env.save` value only after
it is proven obsolete. Secure deletion is intentionally not inferred from age
alone. No runtime or source path loads `.env.save`; remaining proof requires
revocation/invalidity confirmation from Anthropic before deletion.

from its dedicated Keychain item and the saved historical value from
`.env.save`, sends each only to Anthropic's official models endpoint, and emits
status labels only. It never reads response bodies or renders key material.
